================================================================================
  DATA TRANSFORMATION WORKFLOW
  I/O Payloads at Each Stage of the TRDENG Pipeline
  (Enhanced with Goal & Risk Gating Module, Dead-Day Filter & Stitch MCP UI)
================================================================================

--------------------------------------------------------------------------------
1. DATA PIPELINE OUTPUT  (Input to the Prediction Engine / Brain)
--------------------------------------------------------------------------------
The data pipeline calculates stationary features and passes a raw feature
vector to the Prediction Engine's pre-processor via shared memory or socket.

JSON
{
  "timestamp": 1698245612.405,
  "instrument": "BTC-USD",
  "features": {
    "frac_diff_price_1m": 0.0452,
    "garch_vol_5m": 0.0012,
    "order_book_imbalance": -0.24,
    "rsi_14": 42.1
  }
}

--------------------------------------------------------------------------------
1.5 LIVE TICK FEED & MICROSTRUCTURE ENGINE  (Binance aggTrade → vap_cvd.py)
--------------------------------------------------------------------------------
Live tick data is consumed asynchronously via Binance WebSocket aggTrade stream
and ingested directly into the 500-bin incremental VAP and CVD accumulators.

Raw Inbound WebSocket Tick JSON:
{
  "e": "aggTrade",
  "s": "BTCUSDT",
  "a": 123456789,
  "p": "64215.50",
  "q": "0.185",
  "m": false,
  "T": 1698245612415
}
  Field Notes:
    m : maker flag (false = buyer is taker / aggressive BUY; true = aggressive SELL)

Computed Microstructure State (published to Redis `trdeng:vap_state`):
{
  "instrument": "BTC-USD",
  "timestamp": 1698245612.420,
  "vpoc_price": 64215.50,
  "vah": 64580.00,
  "val": 63890.25,
  "cvd_current": 142.85,
  "cvd_trend": "BULLISH",
  "divergence": "BULLISH_ABSORPTION"
}

--------------------------------------------------------------------------------
2. CORE BRAIN & IFF OVERLAY OUTPUT  (Standardized Signal → Message Broker)
--------------------------------------------------------------------------------
The pre-processor normalizes the features. The ensemble models (Ridge,
XGBoost, LSTM) generate independent predictions. The meta-aggregator weights
them by detected regime, then evaluates the Institutional Flow Score (S_flow)
from alpha_overlay/iff.py. Opposing extreme flows trigger an immediate veto.
The Signal Standardizer formats the result into a unified payload and publishes
it to Redis channel `trdeng:signals`.

JSON
{
  "signal_id": "sig_98a7f62b",
  "timestamp_generated": 1698245612.482,
  "instrument": "BTC-USD",
  "direction_magnitude": 0.65,
  "confidence_score": 0.82,
  "conviction_score": 0.82,
  "dead_day_result": {
    "is_dead_day": false,
    "effective_conviction": 0.82,
    "range_atr_ratio": 1.15
  },
  "regime_flag": "high_volatility",
  "flow_score": 0.21,
  "iff_veto": false,
  "latency_ms": 77
}

  Field Notes:
    direction_magnitude : [-1.0, +1.0]  negative = short, positive = long
    confidence_score    : [0.0,  1.0]   used by Kelly Criterion in EE
    regime_flag         : drives meta-aggregator weight selection
    flow_score          : [-1.0, +1.0]  composite flow score (COT + CVD + OBI)
    iff_veto            : boolean       true if S_flow vetoed the ML signal
    latency_ms          : DP → SS processing time

--------------------------------------------------------------------------------
3. EXECUTION ENGINE OUTPUT  (Proposed Order → Risk Guard)
--------------------------------------------------------------------------------
The Execution Engine pulls the signal from the broker, applies the Half-Kelly
Criterion damped by volatility and multiplied by (1 + S_flow) institutional conviction,
then constructs a formal order proposal for the Risk Guard.

JSON
{
  "order_id": "ord_55b3c19x",
  "signal_id": "sig_98a7f62b",
  "instrument": "BTC-USD",
  "action": "BUY",
  "order_type": "LIMIT",
  "price": 64215.50,
  "quantity": 0.15,
  "portfolio_allocation_pct": 2.5
}

  Field Notes:
    quantity                : derived from f_final = f_damped* × (1 + S_flow)
    portfolio_allocation_pct: % of total portfolio this order represents
    order_type              : LIMIT | MARKET | STOP_LIMIT

--------------------------------------------------------------------------------
4. RISK GUARD EVALUATION  (Order State → OMS or DROP)
--------------------------------------------------------------------------------
The Risk Guard checks the proposed order against global limits in config.py.

  Checks performed:
    - current_drawdown < max_drawdown_allowed
    - current_exposure + portfolio_allocation_pct < max_exposure_pct
    - instrument-level concentration limit (max 25%)
    - VaR budget remaining

  APPROVED path  →  forwarded to OMS for execution
  REJECTED path  →  dropped; workflow terminates for this signal

JSON  (APPROVED example)
{
  "order_id": "ord_55b3c19x",
  "signal_id": "sig_98a7f62b",
  "instrument": "BTC-USD",
  "action": "BUY",
  "order_type": "LIMIT",
  "price": 64215.50,
  "quantity": 0.15,
  "portfolio_allocation_pct": 2.5,
  "risk_state": "APPROVED",
  "risk_check_timestamp": 1698245612.501,
  "checks_passed": ["drawdown_ok", "exposure_ok", "concentration_ok", "var_ok"]
}

--------------------------------------------------------------------------------
5. SIMULATED OMS EXECUTION & VPOC-SNAPPED TAKE-PROFIT
--------------------------------------------------------------------------------
The simulated OMS monitors active positions. Partial take-profit targets are
dynamically snapped to nearest Volume-at-Price structural boundaries (VAH/VAL/VPOC)
if closer than the baseline ATR target (+1.0 ATR / +2.0 ATR).

JSON (OMS Active Position State)
{
  "instrument": "BTC-USD",
  "side": "LONG",
  "entry_price": 64215.50,
  "quantity": 0.15,
  "trailing_stop": 63715.50,
  "tp1_target": 64579.50,
  "tp1_reason": "TP1_VAP_SNAP",
  "tp2_target": 64800.00,
  "tp2_reason": "TP2_+2_SIGMA"
}

================================================================================
  END-TO-END LATENCY BUDGET  (indicative)
================================================================================

  Stage                          Cumulative Latency
  DP  → PP (feature delivery)    ~  5 ms
  PP  → Ensemble models          ~ 20 ms
  Ensemble → MA                  ~ 75 ms
  MA  → IFF Gate (veto/scale)    ~  2 ms
  MA/IFF → SS                    ~  2 ms   (latency_ms in signal payload)
  SS  → MB (publish)             ~  2 ms
  MB  → EE (consume)             ~  3 ms
  EE  → RG                       ~  5 ms
  RG  → OMS (if APPROVED)        ~  5 ms
                                 ----------
  Total (target)                 < 120 ms
