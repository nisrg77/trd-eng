1. EVENT-DRIVEN PHILOSOPHY
--------------------------------------------------------------------------------
TRDENG is an event-driven system operating on strict asynchronous message passing.
Components never call each other's execution routines synchronously. 

Core Invariants:
  1. Non-Blocking Event Loops : No event handler may execute synchronous I/O, 
                                heavy training, or network blocking loops.
  2. Idempotency              : Every event carries a unique `event_id` (UUIDv4).
                                Duplicate events within 500ms are discarded.
  3. Failure Isolation        : An unhandled exception in Strategy A's event handler
                                will NEVER crash the event bus or disrupt Strategy B.
  4. Priority Scheduling      : Fill and Risk events always preempt market tick events.


2. EVENT TAXONOMY & PRIORITY QUEUES
--------------------------------------------------------------------------------
The Event Engine maintains 3 internal priority lanes:

  LANE 0: CRITICAL (Priority: IMMEDIATE / PREEMPTIVE)
  ----------------------------------------------------
  • EVENT_CIRCUIT_BREAKER_TRIPPED : -$1000 loss ceiling or 4% daily limit breached.
  • EVENT_ORDER_FILLED            : Order executed on exchange / simulated OMS.
  • EVENT_POSITION_LIQUIDATED     : Position forced exit / emergency stop.

  LANE 1: EXECUTION & GATING (Priority: HIGH, Target latency: <2ms)
  ----------------------------------------------------
  • EVENT_STRATEGY_SIGNAL_EMITTED : Strategy output (direction, conviction).
  • EVENT_AGGREGATED_SIGNAL       : Blended composite signal from Meta-Aggregator.
  • EVENT_ORDER_PROPOSED          : Proposed position size & leverage.
  • EVENT_GATE_APPROVED           : All 9 risk layers passed; order released to venue.
  • EVENT_GATE_REJECTED           : Order vetoed (Dead-Day, Ceiling, LOB Imbalance).

  LANE 2: TELEMETRY & FEEDS (Priority: STANDARD, Loss-tolerant backpressure)
  ----------------------------------------------------
  • EVENT_RAW_TICK_INGESTED       : Binance `aggTrade` or Alpaca real-time tick.
  • EVENT_BAR_CLOSED              : 1m / 5m / 15m OHLCV bar finalization.
  • EVENT_FEATURES_UPDATED        : TA-Lib / pandas-ta indicators recomputed.
  • EVENT_WEBSOCKET_BROADCAST     : Client UI update (matching SCHEMA.md).

5. BACKPRESSURE, TIMING BUDGETS & DEAD-LETTER QUEUE (DLQ)
--------------------------------------------------------------------------------

5.1 Latency Budgets (Target: End-to-End Decision Loop < 15ms)
  • Tick Ingestion & Feature Buffer Update : < 1.5 ms
  • Strategy Signal Evaluation (Pure Func) : < 2.0 ms
  • Meta-Aggregator Blending               : < 0.8 ms
  • 9-Layer Gating & Risk Verification     : < 1.2 ms
  • Order Dispatch (Simulated OMS)         : < 0.5 ms
  • Order Dispatch (Live CCXT REST/WS)     : < 12.0 ms
  • WebSocket UI Broadcast Dispatch        : < 1.0 ms

5.2 Backpressure Management
  • Fast Market Drop Policy: If incoming ticks exceed 5,000 ticks/sec, 
    intermediate price ticks are collapsed/sampled. Bar aggregation and order fill
    events are NEVER dropped under any circumstances.
  • Worker Isolation: Strategy evaluation runs on a dedicated background ThreadPool
    (max_workers=4) preventing UI WebSocket broadcast stalls.

5.3 Dead-Letter Queue (DLQ)
  • Any event that raises an exception across 3 retries is pushed to `DLQ_EVENTS`
    in memory and appended to `decision_trace.jsonl` with error stack trace.
  • The trading engine continues normal execution without interruption.

5.4 Database Event Dispatch Policy (Zero-Tick Architecture)
  • TICK events NEVER trigger database writes. They are held in RAM and streamed
    via WebSocket to the frontend.
  • ORDER_FILLED / POSITION_MUTATED events trigger immediate asynchronous database
    updates to MongoDB `trades`, `positions`, and `account`.
  • Non-frontend events (gate rejections, decision traces, quota health) are queued
    in memory and written to MongoDB in periodic batch intervals (every 30s-60s)
    to protect system throughput and prevent database connection saturation.
