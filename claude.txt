**Context for whoever implements this:** Patches 1–3 (equity-scaled risk budget, rolling-percentile dead-day filter, micro-buffer veto) are implemented and unit-tested. This prompt is the *next* phase — not new features, but making the existing 9-layer decision pipeline auditable, decoupled, and safe to run unattended in paper trading. Do not change trading logic/behavior unless explicitly stated below; this is a structural hardening pass.

## 0. Ground Rules
- No behavior change to existing gates' pass/fail logic unless a step below says so explicitly.
- Every change must keep the existing 30/30 test suite passing, plus add new tests as specified.
- Do not remove any existing gate. The goal is visibility and safety, not simplification of strategy logic — that's a separate, later decision informed by data from Step 4 below.
- After each step, run the mutation-test pattern already established (temporarily break the change, confirm the new tests fail, restore, confirm they pass) before moving to the next step.

## Step 1 — Consolidate per-symbol state into one owned object

**Problem:** `data_pipeline/dead_day_filter.py` (`_history: dict[str, deque]`) and `alpha_overlay/iff.py` (`_flow_ticks: dict[str, deque]`) are two independent module-level global dicts, keyed by symbol, with no shared ownership and no locking.

**Task:**
1. Create `core/symbol_state.py` with a `SymbolState` class holding:
   - `range_atr_history: deque` (maxlen=252)
   - `rvol_history: deque` (maxlen=252)
   - `realized_vol_history: deque` (maxlen=252)
   - `flow_ticks: deque` (maxlen=500) — `(timestamp, flow_score)` tuples
   - A `threading.Lock` (or `asyncio.Lock` if the pipeline is async — confirm which before implementing) guarding all mutation methods.
2. Create a single `SymbolStateRegistry` (module-level singleton, `Dict[str, SymbolState]`) that both `dead_day_filter.py` and `iff.py` read/write through instead of their own private dicts.
3. Refactor `_update_history()`, `_get_percentile_thresholds()`, `_record_flow_tick()` to operate on `SymbolStateRegistry.get(symbol)` instead of local module dicts.
4. **Do not change the percentile math, dwell-time math, or thresholds** — this step is pure state-ownership refactor.

**Verify:** Existing dead-day and micro-buffer tests pass unchanged (only their setUp/teardown needs updating to clear the registry instead of the old module dicts).

## Step 2 — Make the timing/cadence contract explicit

**Problem:** Whether a given layer runs per-bar, per-tick, per-order-proposal, or per-session is currently only inferable by reading each file individually. This is exactly the kind of ambiguity that caused the original Patch 3 staleness concern.

**Task:**
1. At the top of `execution/engine.py`, add a documented cadence table as a comment block:
   ```
   # TRDENG Pipeline Cadence Contract
   # Layer                          | Runs on           | Source file
   # ------------------------------ | ------------------ | -------------------------
   # HMM regime classification      | per bar close      | brain/*.py
   # Meta-Aggregator blend          | per bar close      | brain/meta_aggregator.py
   # IFF opposing-flow veto/scale   | per bar close       (inline, fresh at call time) | alpha_overlay/iff.py
   # Dead-day percentile filter     | per bar close      | data_pipeline/dead_day_filter.py
   # Dynamic leverage curve         | per order proposal | goals/goal_module.py
   # Goal/risk gating               | per order proposal | goals/goal_module.py
   # Micro-buffer dwell veto        | per order proposal, holds hold_ms | alpha_overlay/iff.py
   # LOB imbalance filter           | per order proposal | execution/simulated_oms.py
   # VPOC TP snapping               | per fill / per bar (confirm) | execution/simulated_oms.py
   ```
   Fill in and correct any row where the actual cadence differs from what's listed — this table must reflect verified reality, not assumption; check each source file before finalizing it.
2. Add a short docstring to every gate function stating its actual cadence and its upstream freshness dependency (e.g., "assumes `s_composite` was computed in this same cycle; does not re-validate staleness").

**Verify:** No code behavior changes in this step — documentation and comments only. Confirm nothing in the table is guessed; each row must be traced to actual call sites.

## Step 3 — Add a single decision-trace record per proposed trade

**Problem:** With 9 sequential gates, there is currently no single artifact showing why a given trade did or didn't fire. Debugging requires tracing through 9 files by hand.

**Task:**
1. Create `core/decision_trace.py` with a `DecisionTrace` dataclass:
   ```python
   @dataclass
   class DecisionTrace:
       symbol: str
       timestamp: float
       s_composite_raw: float
       s_flow: float
       iff_veto: bool
       iff_scaled_signal: float
       dead_day: bool
       dead_day_filter_mode: str        # "Percentile P10" or "Static Fallback"
       effective_conviction: float
       leverage: float
       risk_budget_usd: float
       gate_ceiling_blocked: bool
       gate_daily_loss_blocked: bool
       gate_monthly_dd_blocked: bool
       micro_buffer_preempted: bool
       micro_buffer_reason: str
       lob_imbalance_blocked: bool
       final_action: str                # "EXECUTED" | "BLOCKED_<gate_name>"
   ```
2. Thread a single `DecisionTrace` instance through `ExecutionEngine.size_order()`, populated incrementally as each gate runs, rather than each gate independently logging or returning early with no record.
3. On every proposed order — executed or blocked — append the completed `DecisionTrace` to a rolling in-memory buffer (last 1000) and persist to a `decision_trace.jsonl` append-only log file.
4. Expose the last N traces via a new `TRACE_UPDATE` WebSocket message type (or add to existing `GOAL_UPDATE`/`TICK` if simpler) so the Next.js `/trade-logs` view can optionally surface "why was this trade blocked" without needing to read the raw log file.

**Verify:** Add a test that runs a full `size_order()` call through each of the three known cases (dead-day block, circuit-breaker block, micro-buffer preemption) and asserts the resulting `DecisionTrace` correctly reflects which gate fired.

## Step 4 — Replace blocking `time.sleep()` in the micro-buffer hold with a non-blocking implementation

**Problem:** As currently described, `ExecutionEngine.size_order()` calls `time.sleep(hold_ms / 1000.0)` directly in the order-proposal path. Confirm first whether this actually blocks the pipeline for other symbols (i.e., whether `size_order()` runs on the same thread/loop that also processes incoming ticks). If it does, this is a real throughput risk under any meaningful order frequency, not just a style preference.

**Task:**
1. **First: diagnose, don't assume.** Trace whether `run_backend.py`'s main cycle is single-threaded synchronous, or whether it already uses `asyncio`/threading anywhere. Report this before implementing anything.
2. If synchronous: convert the hold-queue mechanism to `asyncio` (`await asyncio.sleep(hold_ms / 1000.0)` inside an `async def size_order()`), with the rest of the tick-ingestion loop running concurrently via `asyncio.gather` or a task queue, so a hold on one symbol's order doesn't stall processing of ticks for other symbols.
3. If already multi-threaded: confirm the sleep is happening on a per-order worker thread, not the main ingestion thread, and that `SymbolState`'s lock (Step 1) correctly protects concurrent access during the hold window.
4. Ensure the veto-preemption behavior is preserved exactly: an opposing flow spike arriving *during* the hold must be able to interrupt/preempt before `hold_ms` fully elapses, not only be checked at hold-expiry. Confirm this against the current implementation — the earlier prose description said dwell-time is evaluated "within that hold window," which is correct in spirit, but verify the actual loop doesn't just sleep-then-check (which would reintroduce the original backward-looking bug in a subtler form).

**Verify:** Add a load test — propose 5+ orders for different symbols within a single hold window and confirm total wall-clock time stays close to `hold_ms` (concurrent), not `hold_ms * order_count` (serialized).

## Step 5 — Cross-layer redundancy audit (data-gathering only, no changes yet)

**Problem:** The HMM regime model and the rolling-percentile dead-day filter both adapt to recent volatility independently, with no shared visibility into each other. It's currently unknown whether they frequently agree, frequently conflict, or one is redundant given the other.

**Task:**
1. Using the `DecisionTrace` log from Step 3, after at least 3–5 days of paper trading, produce a simple report (script, not a UI feature) that computes:
   - Correlation between HMM regime classification and dead-day filter's `is_dead_day` output, per symbol.
   - How often the LOB imbalance filter blocks a trade that the micro-buffer veto also would have blocked (overlap rate).
   - Distribution of `final_action` block reasons across the observed period (which gate fires most/least often).
2. Do not remove or merge any gate based on this data yet — just produce the report. Removing a gate is a strategy decision that should be made deliberately later, with this data as input, not as part of this hardening pass.
